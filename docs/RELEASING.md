# Releasing finance-sync (RELEASING.md)

How releases work, what the pipeline protects, how to roll back, and how the
staging environment is configured.  Companion docs: [MIGRATIONS.md](MIGRATIONS.md)
(migration mechanics), [UPGRADE.md](UPGRADE.md) (per-migration operator notes).

## Release model

Releases are **tag-driven** and fully automated by GitHub Actions
(`.github/workflows/release.yml`).  A push of a `v*` tag runs the whole
pipeline; there is no Hermes/cron involvement and no manual prod step
(other than pushing the tag).

```
v1.2.3 tag push
   │
   ▼
┌─ build ─────────────────────────────────────────────────────────────┐
│ build image (immutable sha tag + semver tag)                       │
│ Trivy scan  (HIGH/CRITICAL fails — same gate/baseline as CI)       │
│ cosign sign (keyless, GitHub OIDC) + verify                        │
│ push to ghcr.io/rbnbrls/finance-sync                               │
└──────┬─────────────────────────────────────────────────────────────┘
       ▼
┌─ migrate ───────────────────────────────────────────────────────────┐
│ alembic upgrade head against an ephemeral PostgreSQL               │
│ ("staging DB") — validates the released migration chain            │
└──────┬─────────────────────────────────────────────────────────────┘
       ▼
┌─ deploy-staging ────────────────────────────────────────────────────┐
│ Coolify API: deploy the staging stack (finance-sync-staging)       │
│ the staging app runs `alembic upgrade head` pre-deployment         │
│ against its own database                                           │
└──────┬─────────────────────────────────────────────────────────────┘
       ▼
┌─ smoke  ⚠ GATE ─────────────────────────────────────────────────────┐
│ /health/live · /health/ready · auth login · GET /transactions      │
│ failure ⇒ pipeline stops — production is never touched             │
└──────┬─────────────────────────────────────────────────────────────┘
       ▼
┌─ promote ───────────────────────────────────────────────────────────┐
│ Coolify API: deploy the production application                     │
│ (also runs `alembic upgrade head` pre-deployment)                  │
└─────────────────────────────────────────────────────────────────────┘
```

### Creating a release

1. Make sure `main` is green (CI, including the Migrations job).
2. Decide the version (SemVer, e.g. `1.2.3`).
3. Create the tag **on the exact commit you want deployed**:
   ```bash
   git fetch origin
   git tag -a v1.2.3 -m "Release v1.2.3" origin/main
   git push origin v1.2.3
   ```
   The Coolify applications build from the repo's `main` branch, so the tag
   should sit on the commit that is (or will immediately be) `main`.  The
   immutable `ghcr.io/rbnbrls/finance-sync:<sha>` image pushed by the
   pipeline is the byte-exact artifact of the tagged commit and the rollback
   reference.
4. Watch the release run in the Actions tab.  Promotion to production only
   happens after the staging smoke tests pass.
5. Manual re-runs: Actions → *Release* → *Run workflow* (optionally pin a
   `ref`).

### The promotion gate

`promote` has `needs: smoke` — the production deploy is only queued when the
staging smoke tests (`scripts/release_smoke.py`) all pass:

- `GET /health/live` — app is serving
- `GET /health/ready` — database and Redis reachable
- `POST /api/v1/auth/login` — authentication works
- `GET /api/v1/transactions` — DB-backed read returns the documented shape

Any failure (or a failing migration job, or a failing Trivy scan) stops the
pipeline before production is touched.

## Staging environment

The staging stack lives in the same Coolify instance as production
(`https://dev.7rb.nl`) but in the **finance-sync project → development
environment**, on the same homelab server.  It is fully isolated from the
production resources: its own PostgreSQL, its own Redis, its own app
container and FQDN.

| Resource | Coolify name | Purpose |
|---|---|---|
| App | `finance-sync-staging` | dockerfile build-pack app from `rbnbrls/finance-sync@main`, port 8000, health `/health/live`, FQDN `https://<uuid>.7rb.nl` |
| PostgreSQL | `finance-sync-staging-pg` | postgres:16-alpine, internal only (not exposed) |
| Redis | `finance-sync-staging-redis` | redis:7-alpine, internal only (not exposed) |

Both the staging and the production apps run

```text
alembic upgrade head
```

as a **pre-deployment command**, so each environment migrates its own
database before the new image starts.  The release pipeline's `migrate` job
additionally validates the full chain on a scratch PostgreSQL before
anything deploys.

### Staging app environment (env reference)

These are set on the `finance-sync-staging` Coolify app (mirrors the
production app's env; values are generated by
`scripts/provision-staging.sh`):

| Variable | Example | Notes |
|---|---|---|
| `APP_ENVIRONMENT` | `staging` | Distinguishes staging logs/metrics |
| `APP_NAME` | `finance-sync-staging` | |
| `DATABASE_URL` | `postgresql+asyncpg://finance_sync:***@<pg-uuid>:5432/finance_sync` | Internal Coolify hostname = DB resource UUID |
| `REDIS_URL` | `redis://default:***@<redis-uuid>:6379/0` | Internal Coolify hostname = Redis resource UUID |
| `SECRET_KEY` | random ≥32 chars | JWT signing secret |
| `MASTER_ENCRYPTION_KEY` | `openssl rand -hex 32` | Credential envelope-encryption key |
| `LOG_LEVEL` | `INFO` | |
| `CORS_ORIGINS` | `["*"]` | |

### (Re)provisioning the staging stack

`scripts/provision-staging.sh` recreates the whole stack from scratch via the
Coolify API (new random credentials each run).  It never touches the
production app or databases.  If the app UUID changes, update
`STAGING_APP_UUID` at the top of `.github/workflows/release.yml`.

## Rollback

Rollback policy is **image rollback + backward-compatible migrations** —
never a blind schema downgrade in production (see `docs/UPGRADE.md` →
*Rollback notes*).  Migrations are expand/contract: each release is
backward-compatible first (old code reads the new schema fine), so the
previous image can always start against the new schema.

### Rollback procedure (production)

1. **Confirm the failing release.**  Check the deployment status in Coolify
   (or the release run in GitHub Actions).
2. **Image rollback.**  Coolify keeps the deployment history per app; the
   simplest rollback is the API endpoint that redeploys a previous commit:
   ```bash
   curl -X POST "https://dev.7rb.nl/api/v1/applications/${PROD_APP_UUID}/rollback" \
     -H "Authorization: Bearer ${COOLIFY_API_TOKEN}" \
     -H "Content-Type: application/json" \
     -d '{"commit": "<previous-green-commit-sha>"}'
   ```
   Alternatively use the Coolify dashboard: application → *Deployments* →
   pick the previous successful deployment → *Rollback*.  Both rebuild the
   previous commit's image, which is safe against the new schema because
   migrations are backward-compatible.
3. **Verify.**  Watch `/health/ready` and a sync run:
   ```bash
   curl -fsS https://<prod-fqdn>/health/ready
   ```
4. **If the previous image cannot start** (a rare breaking migration slipped
   through): restore from backup first (`pg_dump`), then downgrade the
   schema explicitly with `ASYNC_DB_URL=<url> alembic downgrade <previous>`
   — documented per revision in `docs/UPGRADE.md`.  Never downgrade without
   a backup.
5. **Do not re-tag.**  A rolled-back release is fixed forward: revert the
   code on `main`, merge, and cut a new `v*` tag.  Tags are immutable
   pointers to a pipeline run; re-pushing a tag re-runs the full pipeline
   against the same commit.

### Rollback of the immutable image (GHCR)

The `ghcr.io/rbnbrls/finance-sync:<sha>` image for every release is signed
(cosign) and never overwritten.  It is the provenance/forensic artifact for
the rollback — record the sha tag from the release run if you need to audit
exactly what shipped.  To roll the Coolify apps onto a specific image
instead of a git commit, switch the app's build pack to *Docker Image* and
set `ghcr.io/rbnbrls/finance-sync:<sha>` as the image reference
(Coolify dashboard → app → Build Pack).  This is an ops decision per
incident; the git-commit rollback above is the default path.

### Migration safety rules (from docs/MIGRATIONS.md)

- One linear chain, one head — CI fails otherwise.
- Every revision ships a symmetric `downgrade()` and a UPGRADE.md note.
- Expand first (additive, nullable), contract in a later release.
- The app never creates or alters schema at runtime.

## Workflow reference

| Trigger | What happens |
|---|---|
| `push` tag `v*` | Full pipeline: build → scan → sign → migrate → staging → smoke → promote |
| `workflow_dispatch` | Same pipeline for an explicit `ref` (manual release) |
| push/PR to `main` | Unchanged: existing CI (`ci.yml`) — release.yml does not interfere |
